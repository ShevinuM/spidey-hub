# Post-mortem: iteration 6 (2026-08-20)

## Summary

Iteration 6 shipped 8 user-visible defects — dead animations across three
components, a boot/toast timing race that hid every notification on a
visitor's first load, a layout void, clipped/non-scrolling content, and a
missing syntax-highlighting path — while every automated gate reported
green: **335 unit tests, 908 e2e tests (454 spec-level assertions × 2
viewports), and 42 visual goldens all passed** on the commit the defects
shipped in (`cc65f60`; unit count is `pnpm test:unit`'s own total minus the
1 test iteration-7's Phase 1 later added in `tests/unit/keyframes-dedup.test.ts`,
which did not exist yet; e2e/visual counts match the pre-iteration-7 `21`
spec files documented in `docs/architecture.md`).

This is not primarily a discipline failure. It is a structural one: **the
gates, as designed, excluded by construction the exact conditions a real
first-time visitor experiences** — live infinite CSS animation, a cold boot
with no seeded "already visited" flag, and content long enough to overflow
a fixed-size panel. A defect that only exists under those conditions was
invisible to all three suites regardless of how carefully any individual
commit was reviewed.

As of this writing, two of the eight defects have a landed fix and a
regression gate: dead keyframes (commit `b885c18`) and the toast/boot race
(commit `6b6061e`). The remaining six are planned for a follow-up
iteration and are not yet landed; this document does not claim otherwise.

|---|---|---|---|

## Root cause 1 — dead inline-referenced keyframes (defects 1, 5, part of 8)

Svelte scopes a `@keyframes` block declared inside a component's `<style>`
block by renaming it to `svelte-<hash>-<name>`, but it does **not** rewrite
an `animation:` value written in markup's inline `style="..."` attribute.
Every animation in this codebase ported verbatim from the inline-style
`.dc.html` mockups under `UI-Mockups/builds-page-design-review/` (e.g.
`Personnel.dc.html:124`'s `animation:spin {{ node.spinDur }} linear
infinite`, `Builds.dc.html:58`'s `animation:pls 2.4s ease-in-out infinite`)
therefore referenced a keyframe name that did not exist once the
`@keyframes` declaration was scoped by Svelte. The browser silently treated
the reference as unresolved: no animation object was ever created, and no
error was raised anywhere — build, `pnpm check`, console, or test.

Confirmed dead, pre-fix (line numbers as of `b885c18^`, the parent of the
fix commit):

| keyframe | inline reference | dead `@keyframes` declaration |
|---|---|---|
| `senseRing` | `NotificationBell.svelte:27` | `NotificationBell.svelte:43` |
| `toastIn` | `ToastStack.svelte:27` | `ToastStack.svelte:56` |
| `strand` | `ToastStack.svelte:30` | `ToastStack.svelte:70` |
| `panelIn` / `sweep` | `NotificationsPanel.svelte` (inline) | `NotificationsPanel.svelte:156`/`166` (pre-fix) |
| `spin` / `rspin` / `spark` / `dash` | `TimelinePanel.svelte:107,114,52,61/66` | `TimelinePanel.svelte:138/143/148/164` |

`drain` (`ToastStack.svelte:94`, pre-fix) was the one exception: its
`animation:` declaration sits inside the component's own `<style>` block
(in the `.eh-toast-drain` rule), so Svelte's normal scoping rewrote both
the declaration and the reference together, and it worked correctly from
day one. That asymmetry is the whole mechanism in miniature: **the failure
mode is not "animations are broken," it is "an inline-style `animation:`
value can never resolve a component-scoped keyframe name."**

Two duplicate, entirely unused `@keyframes pls` blocks also existed
(`ReposPanel.svelte:87`, `StatusPanel.svelte:82`, pre-fix) — both call
sites' inline `animation:pls` references resolved to the *global* `pls` in
`src/styles/global.css` instead, so those two components' dots kept
animating throughout, but the dead component-scoped copies sat as a silent
last-definition-wins hazard.

### Why no gate caught it

- **Visual goldens run under `PORTFOLIO_FIXTURES=1`, which disables every
  `infinite` CSS animation site-wide** (`docs/architecture.md`'s "Fixture
  mode" section) — **and** `tests/visual/pipeline.mjs:230` and `:334`
  separately pass Playwright's `animations: "disabled"` to
  `page.screenshot()`. Two independent layers of animation-freezing, either
  one sufficient on its own, meant a dead keyframe and a live one rendered
  an *identical* frame at capture time. The goldens could not have detected
  this defect no matter how many times they were captured.
- **`pnpm test:e2e` had no assertion that any animation actually ran.**
  Nothing in the pre-iteration-7 21 spec files called `getAnimations()` or
  inspected `document.styleSheets` for a matching `CSSKeyframesRule`.
- **The one verification method actually tried during the investigation
  cannot distinguish the two cases.** `getComputedStyle(el).animationName`
  returns the declared name whether or not that name resolves to a real
  keyframes rule — a dead `spin` reference and a live `swp` reference both
  read back a non-`"none"` string. Only `el.getAnimations().length > 0` (for
  animations already running) or a direct lookup against
  `document.styleSheets` for a matching `CSSKeyframesRule` (works for both
  one-shot and infinite animations) can tell them apart. `tests/e2e/animations.spec.ts:8-15`'s
  own header comment states this explicitly ("`getComputedStyle(el).animationName`
  is USELESS for detecting this"). During the iteration-7 investigation that
  produced this document, an `animationName`-based check was tried first and
  did in fact report the dead animations as fine, before the resolution-based
  check replaced it — recorded here as a first-hand account of the
  investigation, not as something the spec file itself narrates.

### Fix and gate (landed)

`b885c18` renamed each dead in-component declaration to Svelte's global
form (`@keyframes -global-senseRing { ... }`, etc. — confirmed present today
at `NotificationBell.svelte:49`, `NotificationsPanel.svelte:162/172`, and
`TimelinePanel.svelte:148/153/158/174`), which keeps the keyframe
co-located with the component that owns it while making it resolvable from
an inline reference. The two duplicate `pls` blocks were deleted. The same
commit added a `@media (prefers-reduced-motion: reduce)` gate on each of
these animations, closing a pre-existing, unrelated `AGENT_CHECKLIST.md`
violation (see "Standing hazards" below).

`tests/e2e/animations.spec.ts` (added in the same change) now asserts every
element's computed `animation-name` resolves to a real
`CSSKeyframesRule` in `document.styleSheets`, plus a `getAnimations()` +
transform-sampling check for the infinite animations specifically.
`tests/unit/keyframes-dedup.test.ts` separately guards against a duplicate
`@keyframes` declaration existing anywhere in `src/` at all — a check the
resolution-based e2e test structurally cannot make, because an unused
declaration has no reference to fail to resolve.

## Root cause 2 — toast/boot race (defect 8)

`src/components/BootSequence.svelte` renders an opaque, unskippable
overlay for `bootMs` (`src/data/boot.yaml:13` = `4600`) plus an `OUT_MS`
fade-out (`BootSequence.svelte:111` = `760`) — roughly 5.36s total. Before
`6b6061e`, `notificationsState.svelte.ts` armed every toast's auto-dismiss
countdown on mount with no awareness of the boot overlay; toast durations
are `info` 3000 / `warn` 5000 / `alert` 10000 ms
(`src/lib/notificationStore.ts:41-43`). Every `info` toast, and most `warn`
toasts, could fully expire while still hidden behind the overlay, so a
cold first-time visitor could see the dashboard finish booting with zero
notifications visible even though several had been correctly spawned.

This was not introduced by iteration 6 — it is latent since the two
features first coexisted (boot: `4401cff`, 2026-08-17; toasts: `285f803`,
2026-08-19). No commit between those two and iteration 6's close ever made
the toast timer boot-aware.

### Why no gate caught it

`tests/e2e/fixtures.ts:52-73`'s shared `context` fixture — used by every
e2e spec except `boot.spec.ts` — pre-seeds the boot-seen `sessionStorage`
key before each test runs, so every other spec's toasts arm and drain under
the assumption boot has already happened. `boot.spec.ts` itself never
mentions a toast. The boot↔notification interaction was therefore
untested from both directions at once: the boot spec never checked
notifications, and every notification spec skipped boot.

### Fix and gate (landed)

`6b6061e` threads `Terminal.svelte`'s existing `bootRef?.isActive?.()`
signal (the same one that already gated keyboard input at
`Terminal.svelte:582`, now also passed to `NotificationsState` via
`Terminal.svelte:919`) into the toast-arming effect, so a toast's countdown
does not start while boot is active and starts immediately once it ends.
Toast durations themselves were left untouched — lengthening them would
have papered over the timing bug rather than fixed it.
`tests/e2e/notifications-boot.spec.ts` (added in the same change) opts out
of the boot-skipping shared fixture the way `boot.spec.ts` does, loads the
dashboard cold, waits for the boot overlay to clear, and asserts at least
one toast is visible with a non-expired drain bar.

A follow-up cosmetic gap surfaced by this fix (not yet landed): the
`drain` bar's own CSS animation still starts at component mount rather
than at the moment a toast is armed, so a cold-boot toast can appear with
its countdown bar already visually fully drained even though the fix
above correctly keeps the toast itself alive. Tracked as a follow-up; the
toast being visible at all — the actual reported defect — is already
fixed by `6b6061e`.

## Remaining defects (not yet fixed as of this commit)

The following are documented here because their root cause and the gate
gap are established, not because a fix has landed. Do not read this
section as "resolved."

- **Defect 3 — employment left panel vertical void.**
  `src/components/employment-records/RecordsPanel.svelte:21` sets
  `justify-content:space-between` on a bordered box wrapping three
  non-growing children (index block, breadcrumb, row list), which spreads
  them to the extremes instead of stacking them from the top. The
  component's own header comment (`RecordsPanel.svelte:2-7`) documents that
  the value was copied verbatim from a mockup's *bottom-anchoring* layout —
  a faithful port of a reference that didn't apply to this component's
  content shape. Introduced in `0a66056` (no earlier version of this
  component exists).
- **Defect 4 — reported as "preview width changes when changing files."**
  Not a width bug: `RecordsPanel.svelte:19` and
  `employment-records/PreviewPanel.svelte:20` both use `flex:1` (→
  `flex-basis:0%`, content-independent). During the iteration-7 investigation
  that produced this document, measuring the preview's rendered width
  across all 6 real records at three viewports showed a constant width at
  every one — the reported symptom is not a width change. The real defect
  is that the preview clips long lines with
  `overflow:hidden` and no wrap and no horizontal scroll
  (`employment-records/PreviewPanel.svelte:39`); different records have
  different line lengths, so the clip point moves between records, which
  reads as the panel resizing.
- **Defect 7 — records list and preview cannot scroll.**
  `RecordsPanel.svelte:21` and `PreviewPanel.svelte:39` use bare
  `overflow:hidden` with no `overflow-y:auto` and no scroll-offset
  mechanism; `repositories/PreviewPanel.svelte:37` has the identical
  defect. Every other list/preview panel in the codebase
  (`FilesPanel`, `ReposPanel`, `CommitsPanel`, `NotificationsPanel`,
  `EditorBuffer`, `HelpView`, `Profile`, `CopyMode`, `ChooseTree`) already
  uses `overflow-y:auto` — only these two panels do not. Introduced in
  `0a66056`. Latent under today's fixture data because the 6 real
  `role.md` files are short enough not to overflow the captured
  viewports — see "structural gaps in fixture data" below.
- **Defect 6 — repositories preview has no syntax highlighting.**
  The generate-time Shiki pipeline (`src/lib/highlight.ts`, introduced in
  `f80d682`) writes per-line token/palette data into
  `public/generated/repos/<name>.json` and wires it into the full-screen
  Editor only. `repositoriesState.svelte.ts`'s `PreviewState` carries only
  plain `lines: string[]`; the always-visible preview panel discards the
  token data that the same file object already carries for the Editor.
  Markdown files get color through a separate, non-Shiki heuristic
  (`src/lib/docline.ts`) — only non-`.md` code files hit the flat,
  single-color fallback.
- **Defect 2 — repositories status/repo dots appearance.** Explicitly out
  of scope for an autonomous fix: the two component-scoped `@keyframes pls`
  duplicates found under root cause 1 were dead, but the dots themselves
  were separately measured moving (their inline reference resolves to the
  global `pls` in `src/styles/global.css`). This complaint is about
  color/size/placement, a visual judgment call requiring the user's
  sign-off before any code change lands.

## On the golden rebaselines: policy-compliant, not the cause

Every golden rebaseline sampled from iteration 6 was tied to a named,
deliberate visual-change commit, and none was used to silence an
unadvertised refactor's diff — the behavior `docs/architecture.md`'s
rebaseline policy exists to prevent. The commits, precisely:

| visual-change commit | rebaseline commit | goldens touched |
|---|---|---|
| `3eb7ce2` (rename Personnel Files → Employment Records) | same commit + `10cad41`, its immediate next commit | 4 in `3eb7ce2` itself, 36 more in `10cad41` |
| `0a66056` (rebuild Employment Records v2) | `b59eb59`, its immediate next commit | 6 |
| `a70f70e` (rebuild Repositories UI v2) | same commit | 6 |
| `3487d1a` (real contribution grid) | `c8a7ad6`, its immediate next commit | 6 |
| `4a64216` (help: teal `PanelBadge` pill, drop ALL-CAPS) | `7b946d8`, its immediate next commit | 2 |
| `51c6ab7` (help: match letter-spacing to mockup) | same commit | 2 |

(Commit order verified via `git log --oneline --reverse`, not inferred from
messages/dates.)

Note the precision this table earns: `docs/architecture.md`'s policy text
says rebaseline "in the same commit" as the visual change; in practice three
of these six landed as an *immediately adjacent, dedicated* follow-up
commit — with zero commits in between — rather than a literal single
commit (`10cad41` immediately follows `3eb7ce2`; `b59eb59` immediately
follows `0a66056`; `c8a7ad6` immediately follows `3487d1a`). The other three
(`a70f70e`, `51c6ab7`, and `3eb7ce2`'s own 4 goldens) did land in the exact
same commit as their visual change. Every one of the adjacent-commit
follow-ups is still a named, single-purpose "rebaseline goldens for X"
commit tied 1:1 to its
visual change, reviewed and committed deliberately — not a diff quietly
folded into an unrelated change to make it pass. **State this plainly: the
rebaseline procedure was followed in spirit throughout iteration 6. The gap
that let 8 defects through was never the discipline of rebaselining — it
was that fixture-mode goldens are structurally blind to live animation and
overflow, so there was never a rendering difference for a rebaseline
decision to catch in the first place.**

## Structural gaps in fixture data

Every fixture (`fixtures/repositories/*.md`, `fixtures/commits/*.json`,
etc., see `docs/how-to-run.md`'s "Fixtures" section) is fixed-length,
synthetic, and tidy by design — it exists to make the visual suite
deterministic, not to stress it. That tidiness is precisely why defects 3
(the void), 4/7 (clipping/non-scrolling), and 6 (highlighting, which
depends on file content that fixtures never varied by language) could ship
without ever producing a pixel difference in a golden: there was never
enough content, or varied enough content, for the layout defect to
manifest during a capture.

run, spanning 3 renames (`3eb7ce2` personnel→employment,

refactors (`fafa178` Builds, `c851af1` Editor, `d2fc9f9` Terminal,

`4a64216`, `0a66056`, `f46bba1`, `3487d1a`, `85d7c31`, `6ade3fd`, `5c08d7f`,

`5c08d7f` (the Notifications folder refactor) is the specific commit that
relocated the toast-arm effect later found to be racing the boot overlay
(root cause 2). Its own added file,
`src/components/notifications/notificationsState.svelte.ts:1-8`, states in
its header comment that the extraction carries "no reactivity, timing, or
behavior change" from the original monolith — a claim about *timing*
specifically, made in a commit that changed zero test files, about code
whose timing bug had already existed since `285f803` and would go
undetected for another full day. The claim was true in the narrow sense
that the relocation itself didn't change behavior (the bug was already
there beforehand) — but it is exactly the kind of claim that a
zero-test-delta commit leaves no way to verify either way.

## Standing hazards found but not caused by iteration 6

- **No `prefers-reduced-motion` gate existed anywhere in `src/`**, despite
  `AGENT_CHECKLIST.md`'s accessibility section already requiring one for
  every `infinite` animation. Every animation repaired in root cause 1 was
  in violation. Fixed alongside the keyframe repair in `b885c18`, not as a
  separate defect.
- **`playwright.config.ts`'s `reuseExistingServer: !process.env.CI`**
  (lines 48 and 68) silently adopts whatever server is already listening
  on its target port — including a stale `pnpm test:visual` server on 4322
  serving a fixtures build with every infinite animation frozen. Two such
  stray servers were found running during the investigation that produced
  this document. Not yet fixed.
- **`scripts/capture-screenshots.mjs:29` hardcodes `PORT = 4323`**, which
  collides with a running `astro dev` (also commonly on a 432x port). Not
  yet fixed.
