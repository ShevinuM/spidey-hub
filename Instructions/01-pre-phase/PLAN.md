Mapping used: `equal`→`toBe`, `deepEqual`→`toEqual`, `notEqual`→`.not.toBe`, `ok`→`toBeTruthy` (single-arg), `match`→`toMatch`, `doesNotMatch`→`.not.toMatch`; a message argument (present on some calls) is carried through as vitest's own optional `expect(value, message)` second parameter. First script run had a bug (a stray empty argument from multi-line calls with a trailing comma before the closing paren, e.g. `assert.deepEqual(\n  a,\n  b,\n)`) that produced syntactically-invalid `expect(a, ).toEqual(b)` output; caught by `tsc --noEmit` before running the suite, fixed in the script, working tree reverted with `git checkout -- tests/unit/` and re-ported cleanly.

One real (not mechanical-artifact) consequence of the port: `assert.ok(x)` is a TypeScript assertion function in `@types/node` (narrows `x`'s type in subsequent code), but vitest's `expect(x).toBeTruthy()` is not — so 6 call sites that relied on that narrowing (`tests/unit/highlight.test.ts` lines around a `TokenSpan[][] | null` result, `tests/unit/githubTrees.test.ts`'s `sessionStorage`-backed `string | null` read) surfaced new `tsc --noEmit` errors after the port. Fixed with non-null assertions (`result!`, `raw!`) at each narrowed use site — behaviorally identical (the preceding `expect(...).toBeTruthy()` already fails the test at runtime if the value were falsy, so the assertion only ever fires on an already-guaranteed-truthy value).
